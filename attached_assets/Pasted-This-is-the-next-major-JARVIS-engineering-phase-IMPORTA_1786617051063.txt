==================================================
PHASE 1 — SIRI-LIKE VOICE EXPERIENCE
==================================================

The current iPhone experience is still wrong.

I want JARVIS to behave as naturally as possible like a voice assistant.

FIRST APP OPEN:

Request microphone permission proactively.

The application should initialize the microphone/voice subsystem on startup so the browser can show the microphone permission prompt as early as the platform allows.

Do NOT wait until the user presses the microphone button.

If permission is denied:
- clearly show MICROPHONE PERMISSION DENIED
- explain how to enable it
- do not repeatedly request permission

If permission is granted:
- initialize the voice subsystem
- show MICROPHONE READY

IMPORTANT iOS CONSTRAINT:
Safari/web apps cannot behave exactly like native Siri.
Do not fake capabilities that iOS does not allow.

Implement the closest reliable web architecture.

==================================================
PHASE 2 — WAKE WORD
==================================================

I want hands-free activation.

When JARVIS is in STANDBY, detect a wake phrase such as:

"Jarvis"
"Jarvis, ci sei?"
"Hey Jarvis"

Wake-word detection should happen locally whenever technically possible.

DO NOT continuously upload microphone audio to the server just to detect the wake word.

When the wake word is detected:

STANDBY
→ WAKE DETECTED
→ LISTENING

The wake phrase itself should NOT accidentally become part of the user's command.

Example:

User:
"Jarvis, che tempo fa oggi?"

JARVIS should process:

"che tempo fa oggi?"

not:

"Jarvis, che tempo fa oggi?"

If continuous listening is not technically possible on iOS Safari, implement a robust fallback and clearly indicate the limitation rather than pretending it is continuous.

==================================================
PHASE 3 — AUTOMATIC END OF SPEECH
==================================================

The user should NOT have to press a button to stop speaking.

Example:

JARVIS:
LISTENING

User:
"Jarvis, come stai?"

User stops talking.

After speech silence is detected:

LISTENING
→ SPEECH ENDED
→ TRANSCRIBING
→ REQUEST SENT

Then JARVIS processes the request automatically.

Fix the current issue where iOS remains stuck in LISTENING.

Handle:
- onresult
- onend
- interim results
- final results
- silence timeout
- recognition restart
- duplicate transcript prevention
- aborted recognition
- permission errors
- Safari interruptions

Never submit the same utterance twice.

PHASE 6 — REAL SELF-REPAIR
==================================================

The current Self-Repair system is a good foundation but needs to become a real engineering recovery system.

Do NOT treat repairs such as:

"set JARVIS_WEB_RESEARCH_ENABLED=true"

as sufficient by themselves.

A repair must identify the actual source of the problem.

Required lifecycle:

INCIDENT DETECTED
→ DIAGNOSIS
→ ROOT CAUSE
→ REPAIR PLAN
→ PATCH
→ TEST
→ VERIFICATION
→ RETRY
→ SUCCESS

or:

INCIDENT DETECTED
→ DIAGNOSIS
→ REPAIR FAILED
→ ROLLBACK
→ REPORT

A repair must never be considered successful until verification passes.

==================================================
PHASE 7 — SEPARATE REPAIR AGENT
==================================================

Create a separate RepairAgent architecture.

The main JARVIS agent remains responsible for normal tasks.

The RepairAgent is responsible for engineering recovery.

Architecture:

MAIN JARVIS
    |
    +---- normal execution
    |
    +---- incident
              |
              v
        REPAIR AGENT
              |
              +---- inspect
              +---- diagnose
              +---- plan
              +---- patch
              +---- test
              +---- verify
              |
              +---- success → retry
              |
              +---- failure → rollback

Create independent configuration for the repair model:

REPAIR_LLM_PROVIDER
REPAIR_LLM_MODEL

Initially it may use the same provider if necessary, but the architecture must allow a different model later.

The RepairAgent must NOT automatically expose all secrets or unrestricted credentials to the model.

PHASE 8 — REPAIR AGENT SAFETY
==================================================

The RepairAgent may:

- inspect relevant source files
- inspect stack traces
- inspect configuration schemas
- inspect tests
- create patches
- modify relevant code
- create tests
- run tests
- verify runtime behavior

It must NOT:

- expose API keys
- print secrets
- blindly rewrite the entire repository
- modify unrelated files
- delete the project
- disable security controls
- disable authentication
- create infinite repair loops
- claim success without verification

Use bounded repair attempts.

Maximum:
3 repair attempts per incident/goal.

If all fail:
stop safely and provide the diagnostic result.

==================================================
PHASE 9 — PATCH + ROLLBACK
==================================================

Repairs must be transactional where practical.

Before modifying code:

create a repair checkpoint / working copy / git-style snapshot.

Then:

PATCH
→ TEST
→ VERIFY

If verification fails:

ROLLBACK

The original working system must be restored.

The incident record must contain:

timestamp

verification result

retry result

All records must be sanitized.

PHASE 10 — CONFIGURATION REPAIR
==================================================

Configuration must have one authoritative source.

Do NOT make a temporary:

If Self-Repair changes configuration:

1. identify the authoritative configuration source
2. update it
3. reload/rebuild runtime settings
4. verify the new value
5. retry the failed operation
6. persist the configuration
7. restart if required
8. verify again after restart

Add a test proving:

incorrect configuration
→ repair
→ persistent configuration fixed
→ runtime reload
→ operation succeeds
→ restart
→ configuration remains fixed
