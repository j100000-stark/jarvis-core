JARVIS — FINAL CINEMATIC AI OPERATING SYSTEM UI

IMPORTANT:
This is the FINAL frontend redesign.

Do NOT modify the existing backend architecture unless a tiny backend change is absolutely necessary to expose a real event/state to the frontend.

Preserve all existing functionality:

- Groq LLM
- ElevenLabs TTS
- SpeechRecognition/STT
- browser SpeechSynthesis fallback
- Memory
- Tools
- AgentOrchestrator
- Security subsystem
- Resilience subsystem
- Watchdog
- Crash recovery
- Network recovery
- DemoBrain
- LocalAIProvider
- API routes
- system status
- execution traces
- safety gates

The goal is to make JARVIS feel like a real cinematic AI operating console.

==================================================
1. CORE PHILOSOPHY
==================================================

JARVIS must NOT look like a normal chatbot.

The user opens the website and immediately sees a living AI system.

The Neural Core is the main element.

The interface should feel:

alive
responsive
technical
cinematic
minimal
intelligent

Do NOT fill the screen with cards.

Do NOT create a generic SaaS dashboard.

==================================================
2. NEURAL CORE
==================================================

The Neural Core is the HERO element.

It must look like a living artificial neural system.

Use Canvas/WebGL with requestAnimationFrame.

Avoid:
- simple CSS scale animations
- predictable loops
- rotating GIF-like spheres
- synchronized particle movement

Each neuron should have independent:
- position
- phase
- speed
- depth
- brightness
- activation probability

Connections should dynamically:
- appear
- disappear
- brighten
- dim
- carry energy pulses

Ambient neural activity should continue while idle.

This ambient activity is visual only.

Never fabricate technical system events.

==================================================
3. STARTUP
==================================================

Startup animation:

0–0.5 sec
BLACK

0.5–1.5 sec
Tiny blue central point.

1.5–2.5 sec
Neurons form.

2.5–3.5 sec
Connections form.

3.5+ sec
System enters IDLE breathing state.

Keep it short.

==================================================
4. IDLE
==================================================

Connected + no active task:

STATE:
IDLE

Neural Core:
- slow breathing
- subtle blue glow
- random small neural activations
- occasional energy pulses
- subtle orbital movement

The system must look alive even when nothing is happening.

==================================================
5. LISTENING
==================================================

When microphone/STT is active:

STATE:
LISTENING

Visual:
- cyan/blue glow increases
- neurons become more active
- subtle inward particle motion
- optional microphone amplitude response

No large:
"TAP TO TALK"
"TAP TO SPEAK"

Keep microphone control small.

==================================================
6. THINKING
==================================================

When Groq is processing:

STATE:
THINKING

Visual:
- increased neural firing
- brighter connections
- faster internal motion
- traveling energy pulses
- stronger blue/cyan glow

Do NOT expose private chain-of-thought.

Only show safe execution status.

==================================================
7. EXECUTING
==================================================

When agents/tools are executing:

STATE:
EXECUTING

Visual:
- localized neural activation
- energy moving between regions
- increased network activity

The activity terminal must show real execution events.

==================================================
8. SPEAKING
==================================================

When ElevenLabs audio actually begins:

STATE:
SPEAKING

The Neural Core must react to actual audio playback.

Visual:
- rhythmic pulses
- increased glow
- energy propagation
- subtle audio-reactive movement

When audio ends:

STATE:
IDLE

Do NOT use a fake fixed speaking timer.

If ElevenLabs fails and SpeechSynthesis fallback is used:
keep SPEAKING state synchronized with actual fallback playback.

==================================================
9. OFFLINE
==================================================

If runtime is unreachable:

STATE:
OFFLINE

Visual:
- very dim
- minimal movement
- frozen/ghost-like neural activity

Never claim the runtime is online when it isn't.

==================================================
10. ALERT SYSTEM
==================================================

Implement a real visual ALERT system.

Normal system color:
BLUE / CYAN

Warning:
AMBER

Error:
RED

Critical:
DEEP RED / HIGH INTENSITY

IMPORTANT:

Do NOT turn the entire screen red.

Only the affected subsystem/event should become red.

Example:

Normal:

> RUNTIME ............. ONLINE
> NETWORK ............. ONLINE
> MEMORY .............. READY

Error:

> NETWORK ............. ERROR
> CONNECTION LOST
> RECOVERY ATTEMPT

Those affected terminal lines should glow red.

The Neural Core should briefly react with a red/amber pulse.

A compact alert card should appear:

⚠ NETWORK ERROR
Connection lost.
Recovery attempt in progress.

==================================================

==================================================

When the system detects an actual failure:

STEP 1:

> NETWORK ........ ERROR

> RECOVERY ........ ATTEMPTING

AMBER

STEP 3:

> NETWORK ........ ONLINE

BLUE

If recovery fails:

> RECOVERY ........ FAILED

RED

SYSTEM ALERT
Network recovery failed.

Use the REAL backend recovery state.

Do NOT simulate successful recovery.
